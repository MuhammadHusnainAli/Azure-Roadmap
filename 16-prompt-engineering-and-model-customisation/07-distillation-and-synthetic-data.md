# Distillation and Synthetic Data

## Why it matters

A frontier model often reaches the quality bar but is too slow or expensive at production volume. **Distillation** trains a smaller, cheaper "student" model to imitate a larger "teacher" on your specific task. The bottleneck is almost always data: you need hundreds or thousands of good examples. **Synthetic data**, generated by a strong model from your documents, APIs or production traffic, fills that gap. Engineers build the data pipeline; architects decide when the savings justify the training and lifecycle overhead; consultants explain the risk of training on generated data.

## Key concepts

### Teacher and student

| Role | Typical model | Job |
|---|---|---|
| **Teacher** | Large or reasoning model (for example GPT-5.x, gpt-4.1) | Produce high-quality outputs for representative inputs |
| **Student** | Small fine-tunable model (for example gpt-4.1-mini, gpt-4.1-nano, gpt-oss-20b) | Learn to reproduce those outputs through SFT |
| **Judge / grader** | Evaluator or LLM judge | Filter bad teacher outputs and compare student vs teacher |

Microsoft's fine-tuning overview describes distillation in Managed Training as **teacher-generated SFT data**: you generate examples with the teacher, then run supervised fine-tuning on the student. Programmed Training (Preview) also offers distillation recipes for custom loops.

### The distillation loop

```text
representative prompts ──► teacher ──► filter/grade ──► training set ──► SFT on student
        ▲                                                                     │
        └───────────── add failures ◄── evaluate student vs teacher ◄─────────┘
```

### Sources of prompts

| Source | Pros | Cons |
|---|---|---|
| **Production traffic** (logged requests) | Real distribution of user inputs | Consent, privacy and retention obligations |
| **Synthetic prompts** generated from documents or API specs | Fast, covers rare cases | Can drift from real usage; needs review |
| **Expert-written prompts** | High quality, targeted | Slow and expensive |

### Stored completions: retired

Azure OpenAI **stored completions** (setting `store=True` on Chat Completions calls to capture conversations, then distilling from them in the classic portal) **retired on 15 October 2026**. Microsoft's guidance is to migrate to the **Responses API and agent traces** as the source of captured interactions. If you read older tutorials that start with "enable stored completions", use logged Responses or tracing data instead. Note that the classic feature required at least 10 stored completions and recommended hundreds to thousands.

### Synthetic data generation in Foundry (Preview)

Foundry has a **Data Generation** feature (**Data → Data Generation**) that turns a single reference file into fine-tuning-ready JSONL:

| Generator | Reference file | Output |
|---|---|---|
| **Simple Q&A** | PDF, Markdown or text under 20 MB | Question–answer pairs; choose long (analytical) or short (factual) answers |
| **Tool use** | OpenAPI 3.0.x/3.1.x JSON under 20 MB | Multi-turn conversations with tool calls over your API |

You choose 50–1,000 samples, the generator model (deployed automatically if needed), and an optional 80/20 train/validation split. Results can be downloaded or sent straight to a fine-tuning job. Only one reference file per job is supported in Preview; combine documents first. Requires at least the **Foundry User** role.

### Quality controls for synthetic data

| Risk | Control |
|---|---|
| Teacher hallucinations copied into the student | Grade outputs with groundedness or a reference check; drop failures |
| Low diversity (many near-duplicates) | Deduplicate; vary prompt templates, personas and difficulty |
| Distribution mismatch with real users | Mix in real (redacted) prompts; evaluate on real traffic |
| Inheriting teacher bias or unsafe content | Run safety evaluators; Foundry also runs a safety check before training |
| Licence and terms | Check that the teacher model's terms allow using outputs to train another model |

## How it works on Azure

| Step | Azure capability |
|---|---|
| Capture prompts | Foundry tracing to Application Insights; application logs; Responses API |
| Generate synthetic inputs | Data Generation (Preview); or your own script calling a model |
| Generate teacher outputs | Batch deployments for 50% lower cost on large volumes ([Topic 15 file 12](../15-foundry-models-and-azure-openai/12-batch-prompt-caching-and-cost-optimisation.md)) |
| Filter | Foundry evaluators (groundedness, relevance, task adherence, safety), OpenAI graders, custom Python |
| Train student | Managed Training SFT (file 06) |
| Compare | Foundry evaluations: student vs teacher vs untuned student on a held-out set |

## Design decisions and trade-offs

| Decision | Guidance |
|---|---|
| **Is distillation worth it?** | Compute monthly teacher cost vs student inference plus hosting plus training and retraining. Distil when volume is high and the task is narrow and stable. |
| **Which student?** | The smallest model that, after tuning, gets within your tolerance of the teacher (for example within 2–3 points on the main metric). |
| **How much data?** | Start with 500–1,000 filtered examples; add targeted examples for failure categories rather than more of the same. |
| **Synthetic or real prompts?** | Real prompts for distribution; synthetic to cover gaps and rare cases. Mix both. |
| **Reasoning teacher, non-reasoning student?** | Common and effective for extraction or classification. For multi-step tasks consider RFT on a small reasoning model instead (file 06). |
| **Keep the teacher in the loop?** | Use a cascade: student first, escalate low-confidence cases to the teacher. This also generates new training data. |

## Hands-on

Distil an invoice-extraction task from a large model to gpt-4.1-mini.

```python
import json, os
from azure.ai.projects import AIProjectClient
from azure.identity import DefaultAzureCredential

project = AIProjectClient(endpoint=os.environ["FOUNDRY_PROJECT_ENDPOINT"],
                          credential=DefaultAzureCredential())
client = project.get_openai_client()

SYSTEM = "Extract supplier, invoice_number, total and currency as JSON."
schema = {"type": "json_schema", "name": "invoice", "strict": True, "schema": {
    "type": "object",
    "properties": {"supplier": {"type": "string"}, "invoice_number": {"type": "string"},
                   "total": {"type": "number"}, "currency": {"type": "string"}},
    "required": ["supplier", "invoice_number", "total", "currency"],
    "additionalProperties": False}}

prompts = [json.loads(l)["text"] for l in open("invoice_texts.jsonl")]

with open("training.jsonl", "w") as out:
    for text in prompts:
        r = client.responses.create(model="gpt-5.5",          # teacher deployment
                                    instructions=SYSTEM, input=text,
                                    text={"format": schema},
                                    reasoning={"effort": "medium"})
        answer = r.output_text
        if not passes_checks(text, answer):                    # your filter: totals add up, fields present in text
            continue
        out.write(json.dumps({"messages": [
            {"role": "system", "content": SYSTEM},
            {"role": "user", "content": text},
            {"role": "assistant", "content": answer}]}) + "\n")
```

Then:

1. Split into training and validation; keep a separate labelled test set.
2. Run SFT on `gpt-4.1-mini-2025-04-14` (file 06).
3. Evaluate teacher, untuned student and tuned student on the test set; record accuracy, latency and cost per 1,000 invoices.
4. Optionally try the portal **Data Generation → Simple Q&A** on a policy document to see generated training pairs.

## Security, cost and reliability notes

- **Privacy.** Production prompts used for training must be covered by your privacy notice and retention policy; redact personal data. Generated data can still memorise sensitive details from reference files, so don't include personal data in them.
- **Batch the teacher.** Generating thousands of teacher outputs is cheapest with Batch deployments.
- **Model collapse.** Training repeatedly on model-generated data without fresh real data degrades diversity. Keep real data in the mix.
- **Preview features** (Data Generation, Programmed Training) have no SLA and can change.
- **Lifecycle.** When the student's base model retires, you must regenerate or reuse data and retrain. Keep the pipeline as code.

## Common mistakes

| Mistake | Fix |
|---|---|
| Training on unfiltered teacher outputs | Grade and filter; drop failures |
| Evaluating the student on synthetic data only | Evaluate on real, labelled inputs |
| Following retired stored-completions tutorials | Capture with Responses API and tracing |
| Distilling an unstable, broad task | Distil only narrow, stable tasks; keep the teacher for the rest |
| Ignoring teacher terms of use | Confirm outputs may be used for training |
| One huge synthetic generation run | Generate in rounds targeted at observed failures |
