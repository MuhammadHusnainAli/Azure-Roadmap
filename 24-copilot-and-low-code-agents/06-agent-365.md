# Agent 365

## Why it matters

Agents are now built in Copilot Studio, Agent Builder, SharePoint, the Microsoft 365 Agents Toolkit, Microsoft Foundry and third-party platforms such as Google Vertex AI and Amazon Bedrock, and they increasingly act like workers: they get @mentioned in Teams, reply to emails and update documents. Organisations need one place to see them all, approve them, control what they access, observe what they do and retire them. **Microsoft Agent 365**, generally available since 1 May 2026, is Microsoft's enterprise control plane for agents. It brings Entra identity, Purview data controls and Defender security to every agent, with a registry and governance experience in the Microsoft 365 admin centre and an SDK so any agent can join. Topic 23 file 10 covered the governance model; this file covers the product itself.

## Key concepts

### Five pillars

| Pillar | Capability |
|---|---|
| **Identity** | Entra-backed **Agent ID** for every agent; agent blueprints define identity and permissions |
| **Observability** | Usage, behaviour and performance across agents; OpenTelemetry from SDK-integrated agents |
| **Governance** | Registry, approval flows, policy templates, rules-based lifecycle management |
| **Security** | Defender detection, risk-based access with Entra, blocking risky agents |
| **Lifecycle** | Onboarding, publishing, updates, retirement; ownerless-agent handling |

### Admin experience (Microsoft 365 admin centre → Agents)

| Area | What admins do |
|---|---|
| **Overview** | Agent counts, hero metrics on impact, top actions (pending approvals, ownership gaps, risks), analytics |
| **Registry** (All agents → Registry) | All agents by publisher type: Microsoft, external partners, published by your org, shared by creator; agents without owners |
| **Requests** | Approve or reject agents submitted for org-wide availability |
| **Agent map** | Visualise agents and their relationships |
| **Policies and templates** | Apply policy templates to agents at onboarding; rules that flag ownerless agents or block risky ones |
| **Access control** | Which users, data, tools and other agents an agent can use |

### Agent types the admin centre recognises

| Type | Built with |
|---|---|
| MCS DA / MCS CEA / MCS BP | Copilot Studio declarative, custom engine and business-process agents |
| Foundry LOB / non-LOB / hosted | Microsoft Foundry |
| Agent Builder | Agent Builder in Copilot |
| SharePoint | SharePoint agents |
| Agent Toolkit | Microsoft 365 Agents Toolkit |
| **Agent instance** | Any agent extended with the **Agent 365 SDK** |

### Agent 365 SDK and CLI

For agents built on any framework (Agent Framework, LangChain, Claude Agent SDK and others; Python, Node.js, .NET), the SDK adds:

- Entra-backed agent identity, optionally with its own resources such as a mailbox;
- notifications from Teams, Outlook, Word comments and email, so the agent participates like a person;
- OpenTelemetry-based observability of interactions, inference events and tool use;
- governed **MCP servers** for Microsoft 365 workloads (Mail, Calendar, SharePoint, Teams) under admin control;
- an IT-approved **blueprint** so every instance inherits compliance, governance and security policies.

The **Agent 365 CLI** automates blueprint creation, identity, Work IQ tools and permissions, MCP integration, publishing and Azure deployment. If built-in integration or registry sync already gives what you need, you don't need the SDK just to register an agent; Vertex AI and Bedrock agents have their own registration path.

### Licensing

| Option | Includes |
|---|---|
| **Microsoft Agent 365** | Per-user licence; works best with Microsoft 365 E5 |
| **Microsoft 365 E7** | Microsoft 365 E5, Microsoft Copilot, Agent 365 and Microsoft Entra Suite |
| **Microsoft 365 / Copilot licences** | Basic agent management in the admin centre for licensed agents |

From 1 July 2026, Defender's AI agent discovery and posture for Foundry and third-party cloud agents requires Agent 365 licensing ([Topic 23 file 06](../23-responsible-ai-security-and-governance/06-defender-for-cloud-ai-protection.md)). Check the service description for feature availability by plan.

## How it works on Azure

| Azure-side element | Agent 365 relationship |
|---|---|
| **Foundry agents** | Appear as Foundry LOB/non-LOB/hosted agents; publish to Agent 365 for central observability |
| **Foundry Control Plane** | Azure fleet operations (evaluation, guardrails, cost) for the same agents ([Topic 14 file 09](../14-microsoft-foundry-platform/09-foundry-control-plane.md)) |
| **Entra Agent ID** | Identity backbone shared by both ([Topic 02 file 10](../02-identity-and-access/10-microsoft-entra-agent-id.md)) |
| **Custom agents on Azure** (Container Apps, AKS, App Service) | Integrate with the Agent 365 SDK; the CLI can deploy to Azure |
| **Defender for Cloud** | Agent inventory and posture (with Agent 365 licensing), AI threat alerts |
| **Purview** | Data security and compliance for agent interactions |

Onboarding a custom agent (outline):

1. Create an **agent blueprint** with the CLI (identity model and permissions).
2. Add the SDK to the agent; configure identity, notifications, observability and governed MCP tools.
3. Test in Agents Playground, then with tenant-backed capabilities (consent and licensing).
4. Publish; an admin approves it in **Requests**; it appears in the registry with owner and policies.

## Design decisions and trade-offs

| Decision | Guidance |
|---|---|
| **Adopt Agent 365?** | Yes if agents are spreading across platforms and business units, or you need Defender agent posture; licence the users who create or use agents per the licensing terms. |
| **SDK vs registry sync** | Registry sync or built-in integration for visibility; SDK when the agent needs identity, notifications, Microsoft 365 data via governed MCP or deep observability. |
| **Autonomous "worker" agents** | Agents with their own mailbox and presence need strict blueprints, sponsors and access reviews. |
| **Approval workflow** | Require admin approval for org-wide publishing; allow creator sharing in limited scopes. |
| **Rules** | Automate flagging of ownerless agents and blocking of risky ones. |

## Hands-on

1. Open **Agents → Overview** in the Microsoft 365 admin centre; review metrics and top actions.
2. In the registry, filter agents by type and find agents without owners; assign or block.
3. Approve a pending agent request after checking its permissions.
4. Follow a sample (Python + Agent Framework) to build an agent instance with the Agent 365 SDK; observe its telemetry.
5. Publish a Foundry agent and find it in the registry.

## Security, cost and reliability notes

- **Agent identities are privileged**: protect with Conditional Access and reviews; avoid broad Graph permissions.
- **Governed MCP**: prefer Agent 365's governed Microsoft 365 MCP servers over custom Graph integrations with app-only permissions.
- **Licensing cost**: per-user; model it against risk reduction and productivity.
- **Coverage**: confirm which platforms and agent types are visible for your tenant.

## Common mistakes

| Mistake | Fix |
|---|---|
| Treating Agent 365 as only a list | Use approvals, policies, rules and access control |
| Custom agents with app-only Graph permissions | SDK identity and governed MCP |
| Ignoring "shared by creator" agents | Review and govern them |
| Not licensing for Defender agent posture | Plan Agent 365 licences if required |
| No owner process | Sponsors, owner reassignment rules |
