# Azure Arc Overview

## Why it matters

Few enterprises run only in Azure. They have servers in their own datacentres, Kubernetes clusters at factories and stores, SQL Server estates that can't move yet, and workloads in AWS or Google Cloud. Without a common control plane, each environment has its own inventory, policies, security tooling, patching and monitoring, and governance gaps multiply. **Azure Arc** projects resources outside Azure into **Azure Resource Manager**, so they appear in the Azure portal, belong to subscriptions and resource groups, carry tags, obey Azure Policy and RBAC, and can use Azure services such as Defender for Cloud, Azure Monitor, Update Manager and Key Vault. It's the foundation of Microsoft's "adaptive cloud" approach and of Azure Local.

## Key concepts

### What Arc projects

| Resource type | What you get |
|---|---|
| **Servers** (Windows/Linux, physical or VMs anywhere) | Inventory, policy and machine configuration, extensions (AMA, Defender, scripts), Update Manager, managed identity, SSH/RDP via Arc, ESU delivery (file 02) |
| **Kubernetes clusters** (any CNCF-conformant distribution) | GitOps with Flux, policy, monitoring, cluster extensions, custom locations (file 02) |
| **SQL Server** | SQL Server enabled by Azure Arc: inventory, licensing (pay-as-you-go, ESU), best practices assessment, Entra authentication, Defender, backups and migration assessments (file 03) |
| **Azure data services** | SQL Managed Instance enabled by Azure Arc on Kubernetes (file 03) |
| **VMware vSphere and System Center VMM** | Inventory and lifecycle of VMs from Azure |
| **Azure Local** | Arc-based management of Microsoft's on-premises hyperconverged platform (file 04) |
| **Multicloud** | Multicloud connector for AWS inventory and Arc onboarding at scale (file 06) |

### How it works

- An **agent** (the Azure Connected Machine agent for servers; Arc agents in a Kubernetes namespace for clusters) creates an outbound HTTPS connection to Azure: no inbound ports required.
- Each resource gets an **ARM resource ID** and a **system-assigned managed identity**, enabling Azure RBAC and token-based access to Azure services.
- **Extensions** deploy Azure capabilities onto the machine or cluster (monitoring agent, Defender, custom scripts, Key Vault, data services).
- **Custom locations** abstract Arc-enabled Kubernetes clusters as deployment targets for Azure services.
- Connectivity options: public endpoints, proxy, or **Azure Arc private link scope** for private connectivity.

### Control plane, not data plane

Arc manages and governs; workloads and data stay where they run. Most management features are free for servers and Kubernetes (inventory, tags, policy assignment, RBAC); paid features include Defender plans, Azure Monitor ingestion, Update Manager (for Arc servers), machine configuration, and pay-as-you-go licensing.

## How it works on Azure

Onboard a Linux server (interactive) and at scale (service principal or Entra-based onboarding script generated in the portal):

```bash
# On the server (script generated by the portal's "Add a server" experience)
azcmagent connect --resource-group rg-arc-servers --tenant-id <tenant> --location westeurope \
  --subscription-id <sub> --cloud AzureCloud --tags "environment=prod,site=factory-01"
azcmagent show
```

Onboard a Kubernetes cluster:

```bash
az connectedk8s connect -g rg-arc-k8s -n k8s-factory-01 -l westeurope
az k8s-extension create -g rg-arc-k8s -c k8s-factory-01 -t connectedClusters -n azuremonitor-metrics \
  --extension-type Microsoft.AzureMonitor.Containers.Metrics
```

Govern with the same tools as Azure: assign Azure Policy (including machine configuration for OS settings), Defender for Servers, AMA data collection rules and Update Manager schedules at a management group that contains Arc resources.

Query the hybrid estate with Resource Graph:

```kusto
resources
| where type in~ ("microsoft.hybridcompute/machines", "microsoft.kubernetes/connectedclusters")
| extend os = tostring(properties.osName), status = tostring(properties.status)
| summarize count() by type, os, status, location
```

## Design decisions and trade-offs

| Decision | Guidance |
|---|---|
| **Scope** | Onboard all servers outside Azure (including other clouds) for consistent security and inventory; prioritise internet-facing and critical systems. |
| **Resource organisation** | Dedicated subscriptions/resource groups for Arc resources by site or business unit; tags for site, owner, environment. |
| **Connectivity** | Private link scope where outbound internet is restricted; proxies otherwise. |
| **Onboarding at scale** | Use automation (Configuration Manager, Group Policy, Ansible, VMware/SCVMM integration, multicloud connector). |
| **Identity** | Use the Arc managed identity instead of secrets for Azure access from on-premises apps. |
| **Cost** | Turn on paid features deliberately; model Defender and monitoring ingestion costs. |

## Hands-on

1. Onboard a test VM (on-premises, Hyper-V or another cloud) with the Connected Machine agent.
2. Assign an Azure Policy machine configuration that audits an OS setting; review compliance.
3. Deploy the Azure Monitor Agent extension with a DCR and query its data.
4. Connect a Kubernetes cluster (kind/k3s works for labs) and list its resources in the portal.
5. Build the Resource Graph query into a hybrid inventory workbook.

## Security, cost and reliability notes

- **Agent security**: outbound-only, but the agent can run extensions; restrict who can deploy extensions (RBAC, extension allow/block lists).
- **Managed identity tokens** on Arc servers are local; protect admin access to machines.
- **Cost**: free control plane; paid add-ons per server/core or per GB.
- **Connectivity loss**: workloads keep running; management actions queue or fail until reconnected.

## Common mistakes

| Mistake | Fix |
|---|---|
| Treating Arc as a migration tool | It manages in place; migration is Topic 30 |
| Onboarding without tags and resource organisation | Plan structure first |
| Allowing any extension on servers | Extension allowlists and RBAC |
| Ignoring other clouds | Arc-enable AWS/GCP servers too |
| Assuming all Azure features work identically | Check Arc support matrices |
